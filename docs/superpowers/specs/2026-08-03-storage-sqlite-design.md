# Storage: Embedded SQLite — Design

Written 3 August 2026. Covers the "Storage" architecture piece from `docs/superpowers/specs/2026-08-02-phase-1-product-design.md` (see that doc's Storage, Credentials, and Core Loop sections for the product-behavior reasoning this design implements). Tracked in `docs/roadmap.md` under Phase 1.

## Scope

This piece builds the complete storage foundation — schema, migrations, and a typed data-access layer — for every entity the phase-1 spec already describes with concrete fields: tickets, run attempts, review capture, the blocklist, readiness scans, dynamically-discovered credentials, and the single auth account.

Nothing here is wired into a CLI, UI, or pipeline stage yet — those are separate, not-yet-planned architecture pieces (Pipeline shape, Ticket intake, Visibility, Auth all still say "no plan yet" in the roadmap). This mirrors how the Agent engine piece built a complete `EngineInvoker` interface and implementation before any pipeline stage existed to call it. Building the full schema now (rather than growing it incrementally per consuming piece) avoids re-deriving the same relational shape — tickets → runs → reviews — that the product spec has already settled.

## Schema

### `tickets`

| column | type | notes |
|---|---|---|
| `key` | TEXT PRIMARY KEY | matches the ticket queue file's `key` |
| `summary` | TEXT NOT NULL | |
| `description` | TEXT NOT NULL | |
| `url` | TEXT | nullable — queue file's `url` is optional |
| `created_at` | TEXT NOT NULL | ISO 8601 |
| `updated_at` | TEXT NOT NULL | ISO 8601, bumped on every upsert |

Upserted whenever the queue file is read, so a ticket's details stay attached to its run history even if it's later removed from the queue file. Phase 1 has no automatic tracker intake, so this table's only writer is whatever process parses the manual queue file (part of the Ticket intake piece, not this one).

### `runs`

| column | type | notes |
|---|---|---|
| `id` | TEXT PRIMARY KEY | ULID/UUID, generated by the writer |
| `ticket_key` | TEXT NOT NULL | FK → `tickets.key` |
| `engine` | TEXT NOT NULL | e.g. `"claude-code-headless"`, `"claude-code-pty"` |
| `outcome` | TEXT NOT NULL | e.g. `judging`, `implementing`, `verifying`, `ready_for_review`, `needs_human`, `error` — exact enum finalized by the Pipeline shape piece, this column just needs to exist |
| `needs_human_category` | TEXT | nullable; one of the four categories from the product spec when `outcome = needs_human` |
| `needs_human_reason` | TEXT | nullable; free text alongside the category |
| `started_at` | TEXT NOT NULL | ISO 8601 |
| `finished_at` | TEXT | nullable — null while still running |
| `branch` | TEXT | nullable until a branch is actually created |
| `worktree_path` | TEXT | nullable |
| `base_commit` | TEXT | nullable |
| `pr_url` | TEXT | nullable — set once the PR is opened |
| `pr_summary` | TEXT | nullable — the structured summary described in the product spec |
| `created_at` | TEXT NOT NULL | ISO 8601 |

One row per attempt. A ticket can have more than one run over time (the product spec allows manual re-queueing after a failed attempt), so this is a proper one-to-many, not one-to-one.

### `reviews`

| column | type | notes |
|---|---|---|
| `id` | TEXT PRIMARY KEY | |
| `run_id` | TEXT NOT NULL UNIQUE | FK → `runs.id`; unique because phase 1 captures exactly one review per run |
| `merge_outcome` | TEXT NOT NULL | e.g. `merged`, `not_merged` |
| `edit_effort` | TEXT NOT NULL | `merged_as_is`, `minor_edits`, `major_edits` |
| `review_rounds` | INTEGER NOT NULL | |
| `reviewed_at` | TEXT NOT NULL | ISO 8601 |

Split from `runs` because it's filled in later by a human reviewing the PR, independently of the run's own lifecycle, and doesn't exist for runs that never reach `ready_for_review`.

### `blocklist_entries`

| column | type | notes |
|---|---|---|
| `id` | TEXT PRIMARY KEY | |
| `pattern` | TEXT NOT NULL | path pattern or prohibited-action description |
| `reason` | TEXT NOT NULL | |
| `source` | TEXT NOT NULL | `agent` or `human` |
| `proposed_by_scan_id` | TEXT | nullable FK → `readiness_scans.id`; null for human-added entries |
| `created_at` | TEXT NOT NULL | ISO 8601 |

Current mutable blocklist state — the human-editable list the product spec describes (agent proposes via the readiness scan, human adds/removes).

### `readiness_scans`

| column | type | notes |
|---|---|---|
| `id` | TEXT PRIMARY KEY | |
| `started_at` | TEXT NOT NULL | ISO 8601 |
| `finished_at` | TEXT | nullable — null while running |
| `tech_stack` | TEXT | nullable JSON |
| `test_command` | TEXT | nullable |
| `area_signals` | TEXT | nullable JSON — array of `{ pathPrefix, testToCodeRatio, churnScore }` |
| `status` | TEXT NOT NULL | `running`, `completed`, `failed` |

`area_signals` is stored as a single JSON blob per scan rather than a normalized child table: the product spec doesn't call for querying signal trends across scans (unlike the needs-human categories, which the spec explicitly says get aggregated over time) — a table with no relational query against it yet would be normalization nobody uses. Revisit if that changes.

### `credentials`

| column | type | notes |
|---|---|---|
| `name` | TEXT PRIMARY KEY | the environment variable / credential name the agent asked for |
| `value` | TEXT NOT NULL | |
| `created_at` | TEXT NOT NULL | ISO 8601 |
| `updated_at` | TEXT NOT NULL | ISO 8601 |

Populated only once a human provides a value through the UI form described in the product spec. The "blocker" state itself (agent needs `X` to proceed) is just a run's `needs_human_category`/`needs_human_reason` — there's no separate "pending credential" row.

### `users`

| column | type | notes |
|---|---|---|
| `id` | TEXT PRIMARY KEY | |
| `username` | TEXT NOT NULL UNIQUE | |

| `password_hash` | TEXT NOT NULL | |

Single row in phase 1, enforced by application logic (the Auth piece, not this one), not a schema constraint — the same table shape carries into phase 2's multi-account support without a rewrite.

### `sessions`

| column | type | notes |
|---|---|---|
| `token` | TEXT PRIMARY KEY | |
| `user_id` | TEXT NOT NULL | FK → `users.id` |
| `created_at` | TEXT NOT NULL | ISO 8601 |
| `expires_at` | TEXT NOT NULL | ISO 8601 |

### `instance_settings`

| column | type | notes |
|---|---|---|
| `id` | INTEGER PRIMARY KEY CHECK (id = 1) | singleton row |
| `repo_path` | TEXT | nullable until first-run setup completes |
| `first_run_completed_at` | TEXT | nullable |

Holds the repo path chosen via the first-run UI folder picker (product spec Core Loop step 0) — set once via the UI, not hand-edited in the config file, so it belongs in the database rather than `config.ts`'s static config.

## Migrations

Plain numbered `.sql` files under `src/db/migrations/` (e.g. `0001_init.sql`), applied in ascending order at startup by a hand-rolled `migrate(db)` function that tracks applied versions in a `schema_migrations` table (`version INTEGER PRIMARY KEY`, `applied_at TEXT NOT NULL`). No migration library — consistent with this codebase's existing hand-rolled config loader (`src/config.ts`) and guardrails (`src/guardrails.ts`), neither of which reaches for a dependency where hand-rolled logic is straightforward.

`migrate(db)` reads all migration files, compares against `schema_migrations`, and applies any not yet recorded, each inside its own transaction. Running it against an already-up-to-date database is a no-op.

## Data access layer

One module per entity under `src/db/`:

- `src/db/connection.ts` — opens the SQLite file (creating it and its parent directory if absent), enables `PRAGMA foreign_keys = ON`, and runs `migrate(db)`. Exports `openDb(path: string): Database`.
- `src/db/migrate.ts` — the migration runner described above.
- `src/db/tickets.ts`, `src/db/runs.ts`, `src/db/reviews.ts`, `src/db/blocklist.ts`, `src/db/readiness-scans.ts`, `src/db/credentials.ts`, `src/db/users.ts`, `src/db/sessions.ts`, `src/db/settings.ts` — each exports typed row interfaces and functions built on prepared statements (e.g. `insertTicket`, `getTicketByKey`, `listTickets`, `upsertTicket`), taking the shared `Database` instance as their first argument rather than holding module-level state — keeps each module testable in isolation against a throwaway database.

No query builder or ORM (Kysely, Drizzle, Prisma) — raw SQL plus these hand-written repository functions, matching the "don't reach for a library where hand-rolled logic is straightforward" pattern already established in this codebase, and appropriate for a schema this size.

## DB file location & config

`openDb(path: string)` takes the SQLite file path directly — it does not read any config itself. `src/types.ts`/`src/config.ts`'s existing `Config` interface belongs to the prior attempt's pipeline (RSpec/lane-rules-specific, validated against the real `config/pipeline.json` fixture `npm run selftest` uses) and is not touched by this piece, consistent with CLAUDE.md's "one candidate to learn from, not the foundation being extended." Deciding where the path comes from — a new config file/schema for the restarted architecture — is left to whichever future piece actually wires a CLI/UI together; that piece can reuse the same separate-from-`repoPath` pattern `worktreeRoot`/`runsRoot` already established, but that's its call to make, not this one's.

The file still never lives inside the target repo — same reasoning as before, just decided by the caller rather than baked into this piece.

Credentials (`credentials.value`) and password hashes (`users.password_hash`) are stored in plaintext/hashed-but-unencrypted-at-rest, matching the trust boundary the product spec already accepts for VCS credentials living in the hand-edited config file — file permissions on `dataDir` are the actual boundary here, not application-level encryption. Application-level encryption would need a master key stored somewhere else on the same machine, which doesn't raise the actual security bar for a single-tenant local/VPS instance — over-engineering for phase 1.

## Dependencies

Add `better-sqlite3` as a runtime dependency (synchronous API — a natural fit given the product spec's sequential, one-attempt-at-a-time execution model; no need for async DB calls in a single-process, single-run-at-a-time system). Works on Node 20+, unlike `node:sqlite` (experimental/version-gated to Node 22.5+/24+, and this project's `engines` field currently allows Node 20).

Like `node-pty`, `better-sqlite3` ships a prebuilt native binary. `CLAUDE.md`'s existing working rule about `node-pty`'s `spawn-helper` executable bit after a fresh install is the precedent — this plan's first task should confirm `better-sqlite3` loads correctly right after install, and `CLAUDE.md` gets a matching note if any gotcha turns up.

## Testing

Same hand-rolled style already used for the engine tests (`src/engine/*.test.ts`): plain `node:assert`, `testX(): void` functions, `console.log("PASS: testX")`, a `main()` that calls them all, run via `node dist/db/<name>.test.js`. Each test opens a real temporary SQLite file (via `node:fs`'s `mkdtempSync`) rather than mocking the database — SQLite is free and local, so faking it would only test the mock. Coverage per module: migrations apply cleanly on an empty database and are a no-op on a second run, and each entity's insert/get/list/update round-trips correctly.

## Explicitly out of scope for this piece

- Modifying `src/types.ts`/`src/config.ts`'s `Config` — that belongs to the prior attempt's pipeline, not the restarted architecture. Where the DB file path comes from in a real run is left to whichever future piece wires a CLI/UI together.
- Wiring any of these tables into a CLI command, the web UI, or a pipeline stage — that's the job of Ticket intake, Pipeline shape, Visibility, and Auth respectively, none of which are planned yet.
- The exact `outcome` enum values for `runs` beyond what's needed for the column to exist — finalized when the Pipeline shape piece is planned.
- Any encryption-at-rest for credentials or password hashes beyond what's noted above.
- A normalized `area_signals` table — revisit only if cross-scan querying of readiness signals becomes an actual need.
